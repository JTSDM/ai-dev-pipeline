# Grill 三层问题库

> Grill 的目标**不是问完所有问题，而是消除关键歧义**——达到"能写出可验收的 SPEC"即可停止。
> 三层结构：核心 10 问必问 → 领域扩展按需选取 → 深度拷问仅 L 档且每轮 ≤15 问（可分批）。

## 第一层：核心 10 问（必问）

> L 档完整提问；M 档作为 Spec 前自检清单（只确认是否有明确答案或可合理默认，不展开追问；答案缺失且影响 Spec → 对该问触发 mini-Grill ≤5 问）。

1. **目标**：这次要达成的目标是什么？做成什么样算成功？
2. **用户**：谁是使用者？他们的核心诉求是什么？
3. **边界**：范围边界在哪？哪些明确不做（非目标）？
4. **非目标**：现在不做什么？未来可能做什么但本次不做？
5. **数据来源**：数据从哪来？格式、量级、更新频率？
6. **验收标准**：怎么证明做完了？可观察的成功指标是什么？
7. **风险**：最大的风险/失败模式是什么？哪里最可能错？
8. **依赖**：依赖哪些系统/第三方/前置条件？失败怎么办？
9. **术语**：关键名词都指什么？有没有一词多义？（联动 CONTEXT.md）
10. **成功指标**：业务上怎么看这个功能是否成功？（与 6 的区别：业务效果 vs 工程验收）

## 第二层：领域扩展 20-30 问（按项目类型选取）

### API / 后端类
- 接口的调用方是谁？同步还是异步？
- 鉴权/权限粒度？（用户/角色/租户）
- 限流/配额策略？
- 幂等性要求？
- 错误码与错误响应结构？
- 数据一致性与事务边界？
- 缓存策略与失效时机？

### 前端 / 交互类
- 目标设备/分辨率？（移动/桌面/混合）
- 状态管理放哪？页面刷新后状态怎么恢复？
- 加载/空/错误三态怎么展示？
- 表单校验规则与交互时机？
- 无障碍（a11y）要求？
- 主题/多语言需求？

### 数据处理类
- 数据量级？读多写多？
- 数据清洗/校验规则？
- 大数据量下的分页/流式处理？
- 数据归档与保留策略？
- 敏感数据脱敏要求？

### 重构 / 存量改造类
- 现有行为哪些必须保持？（回归红线）
- 哪些代码是死代码可以删？
- 迁移策略：大爆炸还是渐进？
- 兼容层要保留多久？
- 现有测试覆盖如何？缺口在哪？

## 第三层：深度拷问 40+ 问（仅 L 档，每轮 ≤15 问，可分批）

> 用于新项目/新模块/架构级决策。按设计树逐分支走，解决决策间依赖。

### 架构与模块
- 模块划分依据是什么？边界在哪？
- 哪些模块应该是 Deep Module（功能藏在简洁接口后）？
- 模块间依赖方向如何？有没有循环依赖？
- 技术选型的否决条件是什么？
- 演进路径：一年后这个架构会怎么变化？

### 数据与领域模型
- 领域模型的核心实体与关系？
- 实体标识（ID）策略？
- 数据所有权：谁写谁读？
- 多租户/多用户隔离粒度？
- 数据迁移/版本化策略？

### 质量与可观测
- 错误如何被观测到？（日志/指标/告警）
- 性能预算（P95 延迟、吞吐）？
- 安全威胁模型：最可能的攻击面？
- 合规要求（数据出境/存储/审计）？
- 测试金字塔：单测/集成/E2E 怎么配比？

### 交付与运维
- 部署方式与环境划分？
- 回滚策略？
- 配置管理放哪？
- 监控告警的 owner 是谁？
- 文档要求（API 文档/操作手册）？

### 业务与不确定性
- 需求来源的置信度？哪些是猜测？
- 如果业务方向变了，最可能怎么变？
- 哪些决策今天做、哪些可以推迟？（延迟决策原则）
- 上线后 30 天最想验证什么假设？

## 提问纪律

- 一次只问一个问题，等回答后再问下一个（Matt 的 grill 风格）。
- 每个问题背后尽量说清"为什么问"（上下文），帮被问者理解意图。
- 达到"能写出可验收 SPEC"立即停止，不追求问完。
- 所有答案实时写入 DECISIONS.md；未决问题标记"待定"并指定验证时机。
